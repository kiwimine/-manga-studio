# 踩過的坑

這份文件記錄**實際犯過的錯**，以及從中得到的結論。

寫在前面：本專案有兩次「自信地判斷錯了」，都是因為測試方法有問題，而不是被測對象有問題。

---

## 一、用合成測試圖評估真實模型（最嚴重）

### 發生什麼

我手上一個純文字模型（無法看圖），要評估本地 vLLM 模型的視覺能力。
我用 PIL 畫了幾張簡單圖形當「測試圖」，餵給 vLLM，然後根據它的回答判斷能力好壞。

結果我畫了一張「六根手指」的圖，模型判 `PASS`，我就得出結論：

> 「模型視覺能力不可靠，它判斷鬆散、在提示詞誘導下迎合。」

基於這個結論，我改了三輪審查提示詞企圖讓它「更嚴格」。

### 後來發生什麼

用戶用**真實 Qwen-Image-2.1 生成圖**測試，同一個模型立刻正確指出：

- 多出來的那隻手「與地面接觸不自然，疑似穿模」
- 手指「融合或過長」
- 遮色片「邊緣極其銳利，與周圍柔和光影形成強烈對比」

三項瑕疵全部抓到，描述精確。

### 為什麼會錯

我畫的「幾何色塊圖」對模型來說**就是極簡風格插畫**，沒有生成瑕疵。
它判 PASS **是正確的**。是我拿一張沒問題的圖去證明它有問題。

### 結論

**評估模型能力需要真實素材。** 合成圖只能測管線是否通，不能測能力。

如果當初我有意識到「我無法看圖，卻在評估一個視覺模型」，就不會犯這個錯。

### 後續影響

- 那三輪提示詞改動**都是不必要的**（雖然新的中性框架本身是合理的）
- 我還加了一堆規則層 regex 補救，實測發現**誤判率反而上升**
- 最後把規則層砍到只剩「模型列出 BLOCKER 卻判 PASS」一種明確情況

## 二、規則層用 regex 猜模型的措辭

### 發生什麼

因為擔心模型判定不可靠，我寫了一堆關鍵詞匹配，想在模型「裝沒事」時強制攔截。

```python
_BAD_WORDS = ("畸形", "多餘", "不對稱", "變形", "扭曲", "殘留", "遮擋", ...)
```

### 為什麼會錯

**同一件事，中文和英文會寫法不同；同一個詞在肯定句和否定句意思相反。**

實測結果：

```
"no visible silver badge"          → 正確攔截（特徵缺失）
"no artifact and no error"          → 誤判（有缺陷）← 這是在說「沒有瑕疵」!
"looks like an artifact"           → 正確攔截
"Everything matches perfectly."     → 誤判（觀察太短被觸發）
```

我開始用合成字串測規則，結果準確率在 2/4 ~ 6/7 之間來回盪。
**用合成資料測試基於真實分布的規則，本身就是錯的方法。**

### 結論

**不要用 regex 去猜模型的自然語言輸出。**

如果規則層要有作用，判準必須是**結構化的矛盾**（例如「issues 裡有 BLOCKER，但 verdict 是 PASS」），而不是內容比對。

最終規則層只保留一種判準：

```python
if verdict == "PASS" and any(i.severity == "BLOCKER" for i in issues):
    verdict = "NEEDS_FIX"
```

## 三、只靠提示詞約束結構化輸出

### 發生什麼

第一版分鏡生成，我在提示詞裡寫「請輸出以下 JSON 格式」，並附上完整範例。

結果模型**完全沒遵守**：

```
我要求：id / duration / shot_size / camera / action / prompt / video_prompt
模型給：shot_id / panel_id / position / shape / background / characters[]
```

`characters` 和 `scenes` 兩個欄位**整個被丟掉**，鏡頭只剩殘缺欄位。

### 解法

改用 vLLM 的結構化輸出（硬約束，模型無法違反）：

```python
body["response_format"] = {
    "type": "json_schema",
    "json_schema": {"name": "output", "schema": SCHEMA, "strict": True}
}
```

套用後欄位 100% 符合，角色/場景/鏡頭全部正確產出。

### 結論

**能用 schema 約束的，不要靠提示詞。** 提示詞是建議，schema 是合約。

補充：schema 的 `description` 欄位也有用。模型看到
`"description": "鏡頭時長，必須是阿拉伯數字加 s，例如 3s"` 才不會填空字串。

## 四、JSON 被 max_tokens 截斷

### 發生什麼

模型輸出結尾被截斷，` ```json ` 的開頭有、結尾的 ` ``` ` 沒輸出來。

原本的正則 ```` r"```(?:json)?\s*(.*?)```" ```` 需要配對的結尾，抓不到就把整段丟棄。

### 解法

改寫成括號平衡掃描器：

- 逐字元掃描，正確跳過字串內的括號與跳脫字元
- 未閉合時自動補齊結尾括號
- 截斷的尾項做回退修補

### 結論

**LLM 的 JSON 輸出永遠要當成可能損壞的輸入。** 必須有容錯解析。

## 五、vLLM 不接受巢狀 content

### 發生什麼

組裝多圖訊息時用了巢狀結構：

```python
[[{"type":"text",...},{"type":"image_url",...}],
 [{"type":"text",...},{"type":"image_url",...}]]
```

vLLM 直接回 400：`ChatCompletionContentPartTextParam: Input should be a valid dictionary`。

### 解法

扁平化：

```python
[{"type":"text"}, {"type":"image_url"}, {"type":"text"}, {"type":"image_url"}]
```

### 結論

**即使文件寫得支援，也要用最簡單的結構。** 巢狀陣列是最常出問題的寫法。

## 六、思考鏈拖慢純觀察任務

### 發生什麼

vLLM 啟動參數有 `enable_thinking: true` 和 `reasoning_effort: medium`。
審查任務也吃到了這個設定。

實測耗時：**8 分鐘**。

關掉後（`chat_template_kwargs: {"enable_thinking": False}`）：

**10–60 秒**。

### 結論

**不是所有任務都需要思考鏈。** 純觀察、看圖分類，思考鏈是負擔。

分鏡生成（需要規劃、編排）保留思考；審查（需要誠實描述）關閉。

## 七、分鏡時間欄位全空

### 發生什麼

schema 裡 `duration` 是 `{"type": "string"}`，沒有約束格式。
模型就填了空字串 `""`。

### 兩個修法（都要）

1. schema 加 `description` 說明格式
2. 後處理填補：空值 → 依景別給預設，並統一成 `N s` 格式

### 結論

**schema 的型別約束不等於內容約束。** 空字串完全合法。

防禦性後處理不能省。

## 八、flexbox 擠掉右側按鈕

### 發生什麼

標題列用 `justify-content: space-between`，標題文字變長後把右側按鈕擠出畫面。

### 修法

```css
h2 { min-width: 0; flex: 1 1 auto; overflow-wrap: anywhere; }
按鈕容器 { flex: 0 0 auto; }
```

另外 `justify-content: space-between` 的容器在窄視窗都會有同樣問題，全域加了 `align-items: flex-start`。

### 結論

**flex 項目預設 `min-width: auto`，不會小於內容寬度。** 長文字一定會撐爆容器。

## 九、路由重複定義導致端點消失

### 發生什麼

用 Python 腳本 patch 主程式時，patch 執行了兩次，
造成 `/api/projects` 等路由重複定義，中間還截掉了 `/api/memory`、`/api/repair`、`/api/lessons`。

FastAPI 對重複路徑不會報錯，只會用最後一個，前面的靜默失效。

### 結論

**改路由後要驗證。** 逐個 `curl` 一次，比讀程式碼可靠。

## 十、一格等於一個鏡頭

### 發生什麼

最初的規則寫「每個分格 = 一個鏡頭」。
用戶指出這是對的理解錯誤。

漫畫分格是**排版結果**（畫面塞不下所以切開），不是**剪輯點**。
照分格切出來的東西會 2.5 秒一切、全 static，完全沒有鏡頭感。

### 解法

**三層並用**，缺一不可：

1. **提示詞**：從「拆分分格」改成「先理解劇情，再設計 3–8 個鏡頭段落」
2. **強制後處理** `enforce_sequence()`：合併相鄰鏡頭、分配運鏡、依字數算對白時長
3. **時間規劃**：開場 4 秒、結尾 4 秒、一般鏡頭不短於 3 秒

### 實測

5 格漫畫 → 4 個鏡頭，平均 4.0 秒，最短 3 秒，全部有運鏡。
（原本：5 格對 5 格、2.5 秒一切、全 static）

### 結論

**光靠提示詞約束不夠，輸出結構也要在程式層強制。**

模型有很強的「照抄輸入結構」傾向，提示詞說得再清楚也會退回最簡單的對應關係。

## 附：我的能力限制

這些坑有個共同根源：**我是純文字模型，看不了圖。**

所以：
- 我沒辦法自己驗證視覺輸出的品質
- 我只能讀模型回傳的文字
- 「模型說它看到了 X」不等於「它真的看到了 X」

正確的驗證流程需要**人當基準**：
你說明圖片的問題 → 模型獨立回答 → 比對兩者。
模型抓到 = 有效；你看到但模型漏了 = 漏判；模型報了但你沒看到 = 誤判。

這套流程不能省略，尤其在評估視覺能力的時候。
