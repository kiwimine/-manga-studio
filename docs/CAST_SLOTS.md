# 角色位（Cast Slot）架構

**版本**：v0.3.0
**取代**：原本「角色外觀由分鏡層鎖定」的設計

---

## 一、為什麼改

原本的設計假設：**分鏡層負責鎖定角色外觀**。

`PROMPT_READ` 硬性規則第 3 條要求把完整外觀描述逐字重複嵌入每個 shot 的 prompt，
理由是「繪圖模型無記憶，這是全片一致性的唯一保證」。

這個假設在新的 pipeline 裡不成立：

- 外觀改由 **MiniMax H3 reference-to-video** 負責，用你自己製作的男女主角參考圖
- 參考圖是**單一真相來源**，prompt 不該再殘留任何外觀描述與它打架
- 分鏡層若仍寫外觀，會造成「提示詞 vs 參考圖」的雙重真相，一致性反而更差

**結果**：`R-CHAR-DRIFT`（角色走樣）這類問題從 pipeline 裡消失，因為它不再是本層的職責。
分鏡層的職責收斂為：**讀懂劇情 → 擺出角色位 → 安排鏡頭與台詞 → 交棒給合成層**。

---

## 二、核心概念

### 2.1 角色位（cast slot）

角色**不是角色**，是**位置**。

| 概念 | 說明 |
|---|---|
| 角色位 id | `女1` `女2` `男1` `路人` — 穩定編號，跨批次不變 |
| 角色位不描述外觀 | 不寫髮色、瞳色、服裝、配件 |
| 角色位只佔位 | 這個位置上有「一個人」，僅此而已 |
| 外觀來源 | 後期由 H3 reference 圖注入 |

**關鍵性質**：`character_ids` 記錄的是「本鏡頭需要哪幾個角色位的參考圖」，
這正是餵給 H3 的 reference 清單。

### 2.2 三類可見實體

原本 `characters` 陣列把「角色」和「視覺元素」混在一起
（實測資料裡 `c2` 是「飛鳥（意象）」，一隻鳥）。

新架構分三類：

| 類別 | 範例 | 編號 | 走哪個欄位 |
|---|---|---|---|
| **角色位** | 女1、男1 | 依性別+序號 | `characters[].slot` |
| **場景** | 教室、河岸 | 依序號 | `scenes[].id` |
| **道具/元素** | 飛鳥、手機、劍 | 依序號 | `elements[].id` |

非人的可見實體走 `elements`，不佔角色位編號。

## 三、資料流

```
漫畫 20 頁
   │
   ├─ 批次 1 (1-6 頁)   ─┐
   ├─ 批次 2 (7-12 頁)  ─┤  每次帶「角色位註冊表」
   ├─ 批次 3 (13-18 頁) ─┤  觸發：已定義的角色位，務必沿用
   └─ 批次 4 (19-20 頁) ─┘
        │
        ▼
   程式層角色位分配器          ← 新增，見 §4
   （跨批次穩定編號，不由模型決定）
        │
        ▼
   SCHEMA_SHOT 結構化輸出
   ├─ characters[].slot     女1 / 男1 / 路人
   ├─ elements[]            非人可見實體
   ├─ scenes[]
   └─ shots[].character_ids  → 未來 H3 reference 清單
        │
        ▼
   enforce_sequence()        鏡頭合併、時長、運鏡（不變）
        │
        ▼
   產出：劇情流程 + 台詞 + 角色位編排，無任何外觀描述
```

## 四、角色位分配器（核心新增元件）

### 4.1 為什麼需要程式層約束

20 頁 ÷ `BATCH_PAGES=6` = 4 批。第 4 批的 prompt 會帶入第 1–3 批累積的角色位。

**光靠「餵前一批結果給模型看」不能保證一致性。** 模型看到一個新女性角色可能自行發明 `女1`，
與第 1 批的 `女1` 衝突。PITFALLS 第十條的教訓是：
**光靠提示詞約束不夠，輸出結構也要在程式層強制。**

### 4.2 規則

1. **編號依首次出場順序**，不由模型決定最終 id
2. **性別分類由程式層判定**，模型只需標註性別
3. **跨批次不重複編號**：新角色接續既有最大序號
4. **未指定性別者 → `路人`**，共用計數器
5. **程式層做 id 對映**：模型的暫用 id → 正式角色位

### 4.3 對映流程

```
批次 1 回傳：[{id: c1, gender: female}, {id: c2, gender: male}]
  ▼ 分配器
  女1、男1          （首次出場順序）
  ▼
批次 2 prompt 帶入：女1、男1
批次 2 回傳：[{id: c1, gender: female}, {id: c3, gender: male}]
  ▼ 分配器：c1 → 既有「女1」（性別相符）；c3 → 新 → 男2
  ▼
批次 3 帶入：女1、男1、男2
```

程式層的對映判準：性別相符 + 首次出場順序最接近 → 視為同一人。

## 五、Schema 改動

### 5.1 角色位

**舊**：
```json
{
  "id": "c1",
  "name": "男孩",
  "role": null,
  "appearance_en": "short spiky black hair, large round eyes, ...",
  "personality": "...",
  "ref_prompt": "a young boy with short spiky black hair..."
}
```

**新**：
```json
{
  "id": "女1",
  "slot": "女1",
  "gender": "female",
  "first_page": 1,
  "count": 8
}
```

移除：`name`（具體名）、`role`、`appearance_en`、`personality`、`ref_prompt`
新增：`gender`（供分配器判定）、`first_page`、`count`（出現次數）

### 5.2 場景

**舊**：`{id, name, description_en}`
**新**：`{id, name, description_en, first_page}`

場景**保留**外觀描述。場景的一致性由 prompt 承載，不由 reference 圖負責，
這跟角色位不同。`description_en` 仍需逐字沿用。

### 5.3 鏡頭

`shots[]` 結構**完全不變**，`character_ids` 語義改為：
「本鏡頭需要哪幾個角色位的參考圖」。

新增欄位 `element_ids`：本鏡頭出現的非人可見實體。

## 六、提示詞改動

### 6.1 PROMPT_READ

**刪除**硬性規則第 3 條（外觀逐字嵌入）
**改為**：

```
【角色位規則 —— 最高優先級】
1. 角色**不描述外觀**。禁止在任何 prompt 中寫入髮色、瞳色、膚色、身高、
   體型、服裝、配件等任何外貌特徵。
2. 每個角色指派一個穩定編號：女1 女2 男1 男2 路人。
3. 編號依**首次出場順序**分配，一旦賦予不得更改。
4. shot 的 character_ids 填角色位編號，這是後期合成時的參考圖清單。
5. action / dialogue 可以提及角色位（「女1 轉頭」），但只描述動作與情緒。
6. 非人的可見實體（動物、物件、意象）走 elements，不佔角色位編號。
```

### 6.2 PROMPT_SUMMARY

角色速查段落改為角色位對照表：

```markdown
## 2. 角色位
| 編號 | 出場 | 首次頁 | 氣質（僅劇情定位） |
|---|---|---|---|
| 女1 | 8 次 | p1 | 主導情緒線的主角 |
| 路人 | 12 次 | p3 | 背景人群，不需特寫 |
```

### 6.3 build_sheet_prompt / build_art_bible

改用角色位，不引用外觀。`build_sheet_prompt` 產出的英文提示詞
**本身也不含外觀**——因為它同樣要餵給合成模型。

### 6.4 build_art_bible

「角色速查」改為「角色位」：編號、出場次數、情緒定位、建議景別。
**不寫任何外觀描述。**

## 七、repair_module 改動

### 7.1 R-CHAR-DRIFT 改寫

**問題**：現有 `fix_prompt` 指示「把完整外觀逐字貼到每個 prompt 開頭」，
這在新架構下是主動傷害——它會重新引入外觀描述，與 H3 參考圖衝突。

**改寫為**：

- `trigger`：保留（症狀描述方式不變，使用者的描述方式不該被迫改變）
- `cause`：改為「角色位指涉不明確」
- `fix_prompt`：改為強化角色位在動作描述中的明確指涉
- `fix_negative`：清掉外觀類負面詞

### 7.2 PROMPT_DIAGNOSE

刪除「角色設定逐字保留，不可改寫、不可簡化、不可省略」——這條規則
在新架構下指向的東西已不存在。改為「不得新增任何外貌描述」。

## 八、既有資料遷移

`projects/` 下既有 JSON 皆為舊格式（已確認 `c2` = 飛鳥意象）。

策略：**保留原檔不動**，另存為 `<pid>.legacy.json`，供對照。
載入時自動偵測格式並轉換：

```
舊格式（characters[].appearance_en 存在）→ 轉換：套用分配器規則，
     依首次出場順序重新編號為角色位，appearance_en 丟棄
新格式（characters[].slot 存在）→ 直接使用
```

### 8.1 舊 prompt 的處理（實作時發現的問題）

**遷移只能轉換角色欄位，無法清除已生成的 shot 內文。**

實測發現舊資料的 `shot.prompt` 本身就內嵌外觀描述：

```
SH04.prompt: "extreme close-up of a young boy's face, short spiky black hair,
             large sparkling eyes, ..."
```

這類文字**不是**欄位結構的一部分，無法用 schema 改變或欄位刪除來移除。

**處置**：遷移時將原文保留於 `shot._prompt_legacy`，並在專案層標記
`_migration_note`，提醒這些鏡頭需要重寫提示詞才能投入新流程。

**刻意不實作自動清洗。** 理由見 PITFALLS 第二條：用 regex 從英文提示詞裡
剝除外觀描述，本質上還是在猜自然語言——「blonde」可能是頭髮、也可能是布料，
「eye」出現在 `close-up of the eyes`（敘事）與 `dark eyes`（外觀）意義完全不同。
自動清洗會製造一種「看起來乾淨但悄悄改壞」的結果，比留著原文明顯更糟。

正確做法是讓模型依角色位規則重寫，用 `/api/repair` 或重新產生分鏡完成。

## 九、實作後的發現

以下三點是實作與實測後才浮現的，不是設計階段想到的。

### 9.1 模型會無視禁令自行描述外觀

**現象**：即使 `PROMPT_READ` 明列「禁止寫入任何外貌特徵」，模型仍產出：

```
SH02.prompt: "a man wearing a black cap and a dark blue shirt, ..."
SH02.action: "char_01 正面半身像：黑色塊狀短髮、膚色圓頭、深藍色方形上身"
```

**原因**：模型有強烈的「照抄輸入結構」傾向（PITFALLS 第十條記錄的模式）。
`prompt` 欄位要求「描述畫面」，而畫面裡有人——模型自然會描述人的外貌。
它不是不聽話，是**不知道 `prompt` 該寫什麼替代內容**。

**兩處修正**：

1. **提示詞**：在 `PROMPT_READ` 新增「`prompt` 欄位該寫什麼」段落，
   給出正反範例，並明確說「把參考圖放到正確位置、做正確的事」。
2. **程式層偵測**：`detect_appearance_leaks()` 掃描每個鏡頭，
   把殘留回報到 `result.appearance_leaks`，前端顯示警告。

### 9.2 刻意不做自動清洗

偵測到殘留後，**不自動刪除**。理由見 PITFALLS 第二條。

詞彙歧義是實質的：

| 詞 | 外觀用法 | 敘事用法 |
|---|---|---|
| `eyes` | `dark eyes, sharp focus` | `close-up of the eyes` |
| `short` | `short black hair` | `a short pause` |
| `skin` | `skin-tone head` | `skin of the lake`（少見但存在） |

因此偵測器只挑**歧義性低**的詞（`hair`、`wearing`、`uniform`、`blonde`…），
`eye` 刻意放行。自動清洗會製造「看起來乾淨但悄悄改壞」的結果。

正確處置：由 `/api/repair` 讓模型依角色位規則重寫。

### 9.3 LLM 回應的非確定性截斷

**現象**：同樣的 `PROMPT_SUMMARY`、同樣的輸入，兩次呼叫結果差異極大：

| 呼叫 | 結果 |
|---|---|
| 獨立行程測試 | 6086 字，五段落齊全 |
| 背景任務內 | **30 字**，斷在 `> **` |

`run_analysis` 的 `except` 沒有觸發（否則 log 會印「失敗」），
代表 `build_art_bible` 真的回傳了那 30 字。

**修正**：兩處加完整性檢查

- `build_art_bible`：驗證 `## 1.`～`## 5.` 五個標頭齊全，
  缺失則重試（最多 3 次，並把缺失段落回饋給模型）。
- `build_sheet_prompt`：驗證 `PROMPT:` 段長度 ≥ 40 字。
  **舊實作在缺標籤時會退化成 `txt.strip()[:800]`**，
  把整段回應（含 `NOTES:` 的中文說明）當成生圖提示詞餵給模型——靜默劣化。

實測：第一次缺 `## 5.`，重試後拿到完整 5748 字。

## 十、已知限制

**視覺驗證仍需人工。** 分鏡層看不見圖，合成層的品質判斷繞不回本層。
PITFALLS 附錄的限制依然成立。

**角色位一致性靠程式層約束，不保證語意正確。** 分配器能保證編號穩定，
但無法保證「第 17 頁的男性角色」一定被判成 `男1` 而非新開 `男2`。
若模型誤判，會多出一個角色位——這需要人工檢查角色位清單。

**場景一致性仍是弱項。** 場景靠 `description_en` 逐字沿用，
跨 4 個批次的漂移無法完全避免。
